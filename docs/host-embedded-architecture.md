# 上位机 / 下位机 分工架构设计

**日期**：2026-09-16
**状态**：设计已确认，待实现

## 1. 背景与约束

### 硬约束：EtherCAT 总线只能接一台机器

关节的 EtherCAT 总线**物理上只能接到上位机（PC）或下位机（ARM）之一**，不可能两台都直接控制。
但需求是**两边都能操作**——本地（设备旁）和远程（PC）都要能控制。

→ **因此必须有一层网络协议**：接总线的那个当主站，另一台通过网络访问。
这是架构的起点，不是可选项。

### 选定拓扑：ARM 当主站

```
关节 ──EtherCAT──► ARM 板（主站 + 本地界面 + 网络服务）   ← 唯一接总线的
                        ▲
                        │  TCP / WebSocket
                        ▼
                  PC 上位机（远程界面，纯客户端）        ← 不碰总线
```

**为什么选 ARM 当主站**：
- ARM 就在设备旁，本地界面不受网络影响，断网也能操作
- 实时性：ARM 本地跑控制回路，不依赖网络
- PC 端变成纯客户端 → 可以自由选择技术（QML 或 Web），不受实时性约束

## 2. 控制权（核心设计）

「两边都能控制」如果不加约束，就是**两个界面同时往驱动器写命令**——最后一个写的生效，电机行为不可预测。

**这个坑已经踩过**：官方串口调试工具和 EtherCAT 抢控制权时，驱动器停在「禁止合闸」不接受任何控制字。现在同一个坑会变成 PC vs ARM，而且更危险（两边都在发运动指令）。

### 2.1 状态机

```
        ┌──────────────┐
        │   NONE       │  初始态
        └──────┬───────┘
               │ PC 请求 + ARM 授权
        ┌──────▼───────┐
        │   REMOTE     │  PC 持有：PC 可操作，ARM 本地置灰（急停除外）
        └──────┬───────┘
               │ ① ARM 本地「收回控制」（即时生效）
               │ ② PC 心跳超时（自动收回）
               │ ③ PC 主动交还
        ┌──────▼───────┐
        │   LOCAL      │  ARM 本地持有：本地可操作，PC 置灰
        └──────┬───────┘
               │ ARM 本地「允许远程」
               └──────► REMOTE
```

### 2.2 三条安全规则（必须实现，不是可选项）

**规则 1：仲裁权在 ARM，PC 只能请求**
控制权由主站说了算。PC 端没有「夺取」能力，只有「请求」。避免两边都以为自己在控制。

**规则 2：任何控制权切换 → 立即失能所有轴** ⚠️

如果 PC 正在跑位置指令，ARM 此时收回控制权——**驱动器仍按 PC 最后一次下发的目标继续运动**，而 ARM 操作者完全不知道目标是什么（界面上的输入框还是旧值）。

→ 切换时先 `disable()` 所有轴；接手方必须重新「使能」才能运动。

**规则 3：心跳超时自动收回** ⚠️ 最重要

PC 持有控制权时若网络中断：PC 发不出停止命令，ARM 本地界面又是灰的 → **两边都停不了电机**，只剩硬件急停。

→ PC 周期性发心跳（建议 200ms），ARM 超过 1s 未收到则**自动收回控制权 + 失能所有轴**。

（与现有遥测看门狗同思路：500ms 无遥测即断开。）

### 2.3 例外的命令

**急停（ESTOP）不受控制权限制**，两边任何时候都能发。这是唯一例外——安全命令不该被权限挡住。

### 2.4 可见性

两端的界面都必须**显著显示当前控制权**，例如：

```
▶ 控制权：本地（ARM）          或          ▶ 控制权：远程（PC）
```

**无控制权一侧的操作按钮全部置灰**（不是"点了没反应"）——要让人一眼看出为什么点不动。

### 2.5 UI 控件

| 位置 | 控件 | 作用 |
|---|---|---|
| PC 端 | 「请求控制」按钮 | 向 ARM 请求；ARM 授权后生效 |
| ARM 端 | 「允许远程 / 收回控制」二态开关 | 本地永远能即时收回 |

## 3. 网络协议

### 3.1 传输

- **起步：WebSocket + JSON**（调试直观、Qt 客户端/浏览器都支持）
- 若带宽/延迟不够再考虑二进制帧
- Qt 侧用 `QWebSocketServer`（Qt Network 模块自带，**无需引入新依赖**）

### 3.2 下行（ARM → PC）：遥测

**必须降频**。当前是 500Hz × N 从站原始数据直接画；浏览器/远程客户端不需要这个频率。

- **降频到 30~60Hz**（客户端渲染帧率）；由 ARM 侧聚合/抽稀后下发
- 每组遥测含：从站号、时间戳、位置、速度、力矩、温度、状态字、故障码、驱动状态、是否越限
- 附带 **控制权状态、各从站型号/额定力矩**（界面显示需要）

> 附带好处：500Hz 原始数据噪声大（速度差分、力矩纹波），降频聚合后曲线反而更平稳。

### 3.3 上行（PC → ARM）：命令

| 消息 | 说明 |
|---|---|
| `requestControl` | 请求控制权 |
| `releaseControl` | 交还控制权 |
| `heartbeat` | 心跳（仅持有控制权时发送） |
| `selectSlave` | 切换当前从站 |
| `enable` / `disable` / `quickStop` / `faultReset` | 基本操作 |
| `setMode` / `setTarget` | 模式与目标 |
| `homing` / `moveToZero` | 归零 / 回0 |
| `estop` | **不受控制权检查** |

**所有命令（急停除外）在 ARM 侧校验控制权**，无权限时拒绝并回错误。

### 3.4 安全边界

**PC 端不能绕过 ARM 的安全逻辑**。以下全部在 ARM 侧强制执行，不依赖客户端：
- ±170° 行程限位
- 遥测看门狗
- 控制权校验
- 心跳超时收回

客户端只负责"发意图"，**判断与拦截一律在主站**。

## 4. 职责划分

| | ARM（主站 + 本地界面） | PC（远程客户端） |
|---|---|---|
| EtherCAT 主站 | ✅ | ❌ |
| 实时控制回路 | ✅ | ❌ |
| 安全逻辑（限位/看门狗/控制权） | ✅ **权威** | 只显示 |
| 本地界面 | ✅ 现有 Qt 界面 | — |
| 远程界面 | — | ✅ 新建（QML 或 Web） |
| 网络服务端 | ✅ `QWebSocketServer` | — |
| 网络客户端 | — | ✅ |

**PC 端的技术选型（QML / Web+GSAP）不影响本设计**——协议与控制权是技术无关的。选型可另行决定，取决于是否需要浏览器/多端访问。

## 5. 实现分期

| 期 | 内容 | 规模 |
|---|---|---|
| **P1** | ARM 端加 `QWebSocketServer` + 控制权状态机 + 协议 | 中（复用现有 `EthercatDevice`/`ControlWorker`） |
| **P2** | PC 端最小客户端（能连、能看遥测、能发命令） | 中 |
| **P3** | PC 端界面精装（QML 或 Web+GSAP） | 大 |
| **P4** | 多端 / 浏览器 / 平板访问（如需） | 视情况 |

**工作量的大头在 P3（新界面），协议层反而是最容易的一块。**

## 6. 未决事项

1. **PC 端技术选型**：QML（复用 Qt 生态、单栈）还是 Web + GSAP（视觉上限更高、支持浏览器/多端）
2. **协议细节**：JSON 字段定义、错误码、版本协商
3. **是否支持多 PC 同时连接**（建议 P1 只支持单客户端，简化控制权模型）
4. **PC 持有控制权时 ARM 本地急停后**，PC 是否需要收到通知并自动释放控制权（建议：是）
